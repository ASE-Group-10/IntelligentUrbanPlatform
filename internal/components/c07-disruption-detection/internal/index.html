    C07 Disruption Detection: internal interfaces¶

    C07 evaluates disruptions (UC06) and requests separate replanning. Its only HTTP operation, listDisruptions, is a read for C01 (openapi.yaml). The events it consumes are in events.yaml, and its evaluateChange handler is triggered by them. This file covers the calls C07 makes to other components and the record it owns.

    Typed models: backend/app/components/c07_disruption_detection/contracts.py. Conventions (IDs, versions, timestamps, quality, run scope, Result failures): see ../c06-city-monitoring/internal.md.

    Provided interfaces¶

    • listDisruptions (HTTP, openapi.yaml): the Disruption records of live state or one simulation run, for the C01 Disruptions screen (#103). Served by backend/app/components/c07_disruption_detection/router.py from the Postgres store.

    Other components learn about disruptions through the replan requests C07 sends to C05.

    Owned record: Disruption¶

    C10 and C12 will read it, so it should stay stable. Persisted by upsertDisruption. Example: examples/disruption.json.

    Field Type Required Meaning
    disruptionId UUID yes Stable across updates
    version integer yes Bumped only on a material change: status or severity changes, or a new affected plan
    status enum yes active / resolved / unknown
    cause enum yes Same as SegmentCondition cause, plus resource / operational
    severity enum yes low / medium / high. Slice rule: closed on a used segment = high
    segmentKeys / resourceIds arrays yes What is disrupted
    affectedPlans array yes [{ planId, planVersion, replanRequested, replanOutcome, newPlanVersion }]. newPlanVersion is the version C05 saved with PlanSaved, otherwise null, so C01 can show v2 → v3
    triggerEventIds array of UUID yes Every event folded into this record (dedup)
    quality enum yes Confidence in the classification
    createdAt / updatedAt timestamp yes

    Required interfaces¶

    C05 planning operations¶

    C07 requires findAffectedWork(changeScope) and the synchronous, idempotent requestReplan(context, planId, trigger, key). C05 owns their definitions and examples in C05 internal interfaces. C07 uses the returned plan versions and final outcomes to update its disruption record. Both calls carry the run scope and runId of the triggering event. The stale-plan retry and the other points agreed with C05 are in Agreed with C07.

    C06 getCitySnapshot(scope, freshnessPolicy) → Result\<CitySnapshot>¶

    Defined in ../c06-city-monitoring/internal.md. C07 uses it when a CityStateUpdated event does not carry enough context. Not used by the thin slice.

    Decisions (16 Nov 2026)¶

    • [x] Segment keys: seg:<osm_way_id> (OpenStreetMap way ID).
    • [x] Default maxAgeSeconds for freshness: 900 s.
    • [x] Material change that bumps a disruption version: status or severity changes, or new affected plans.
    • [x] Severity rule for the slice: closed on a used segment = high; anything else is out of scope until Iteration 3.
    • [x] findAffectedWork: one C05 call per changed segment for now.
    • [x] requestReplan is synchronous; PublicationPending is dropped from ReplanOutcome.

    Decisions (20 Nov 2026, with C05, #59)¶

    Details and wording are in the C05 section linked above.

    • [x] Run scope: ChangeScope and ReplanRequest carry scope and runId, copied from the triggering event (runId required in simulation, absent in live).
    • [x] Idempotency key: planId:basedOnPlanVersion:disruptionId:disruptionVersion.
    • [x] Any Conflict from requestReplan is a stale plan: C07 calls findAffectedWork once more and retries once with the new planVersion and key. No retry if the plan is no longer affected or the planVersion is unchanged. A retry never changes the disruption version.
    • [x] ReplanOutcome gains reason, required for ReviewRequired. Infeasible is no longer a failure. Remaining failures: Invalid, NotFound, Conflict, Unavailable.
    • [x] PlanSaved is returned once the revision and its PlanReady outbox entry are saved together; publication state stays with C05.
    • [x] PlanningPort returns a typed Result (Ok / Failure) from both calls.
    • [x] retryable is set only when a redelivery can change the outcome: findAffectedWork answering Unavailable (result unknown, event not marked as processed), or a requestReplan not made because C05 answered Unavailable, including the rediscovery after a Conflict (disruption kept, plan not requested).
    • [x] When an event arrives again, C07 sends only the plans still pending, with the same key. Causes a redelivery would not change (NotFound, plan no longer affected, repeated Conflict or same planVersion, Invalid) do not set retryable, so the event is not retried forever.
