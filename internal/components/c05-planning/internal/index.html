    C05 Planning and Replanning¶

    UC03 and UC07 contracts (#32), with the Dublin walking-skeleton implementation tracked in #118. Pair Ye + Zecheng. Bruno accepted external review of #118 and requested Alejandro for the shared C01/C07 and integration changes. Review discussion.

    C05 owns proposals, confirmed plans and revisions. C08 owns actual allocation and operational commitments. Planning reads those facts when checking feasibility.

    Conventions¶

    Use camelCase JSON, UUID v4 identifiers, positive integer versions and UTC RFC 3339 timestamps. Reuse the shared Result<T> from backend/app/shared/result.py. A successful internal call returns Ok(value); a failure returns Failure(kind, message). JSON examples show the success value. PlanningPort returns this Result from both operations and raises no exceptions.

    The adopted C07 models remain in backend/app/components/c07_disruption_detection/contracts.py for compatibility. ChangeScope, AffectedWork, ReplanRequest and ReplanOutcome are the current typed models. PlanningPort in the adjacent planning.py is the current caller interface. The agreements with C07 that shaped them are in Agreed with C07.

    Provided interfaces¶

    generatePlan(delivery, runScope, correlationId, key) → Result\<Plan>¶

    For hop 4 of #72, C04 commits a Dublin simulation delivery before its planning gateway projects the saved row into SavedDelivery and calls app.state.planning.generate_plan in process. C04 owns its delivery row and the authorised read of that row. A successful simulation handoff returns X-Plan-Id, X-Plan-Version and the original X-Correlation-ID alongside the delivery response. On the Deliveries page, Review plan opens that plan in the same run. The saved fields follow the C04 delivery contract.

    Argument What C04 supplies
    delivery A SavedDelivery constructed from the committed C04 delivery. C05 reads deliveryId, version, status, progress.status, cargo.weightKg, constraints.vehicleKinds and timeWindow.
    run_scope A PlanScope with scope="simulation" and the delivery's UUIDv4 runId.
    correlation_id The UUIDv4 from the original delivery request, forwarded through C05 to C09 and C10 and retained for PlanReady.
    key C04 uses c04:{deliveryId}:v{version} when submitting or replaying a delivery. The saved-example importer uses c04:generate:{deliveryId}:v{version}. Both keys stay stable across retries and must be nonblank and at most 200 characters.

    The Dublin proposal uses the Eden Quay segment and one van with the saved cargo weight. Supply the version as a JSON integer, the weight as a JSON number and the delivery window bounds as RFC 3339 UTC strings (for example, 2026-11-20T09:00:00Z). The delivery and its progress must both be pending, and its constraints must allow a van. Departure is the later of the scenario start and the delivery window start. The six-minute route must finish within that window. C05 queries C09 for van delivery in Dublin D1/D2 during the saved window and passes the returned evidence snapshot unchanged to C10. C09 reads the shared live policy corpus and logs the same correlation ID. C10 records the simulation run and the corpus version used for this decision. C10's PlanGenerated decision, the C05 proposal and the generation receipt share one PostgreSQL transaction. A write failure rolls all three back. The first PlanReady outbox entry belongs to confirmation in hop 5.

    Ok(Plan) returns the committed planId, version=1, status="awaiting_confirmation" and decisionId. Retrying the same projected delivery with the same caller, run and key returns that original version. Different projected facts under the same key give Conflict. A signed-in operator with access to the run can read the current version with GET /api/v1/plans/{planId}?scope=simulation&runId={runId}.

    Run hop 4 from the saved delivery example¶

    From the repository root, use the local Compose stack and its migrated database. The last command imports the saved example with its original delivery ID and dates into C04's simulation store. It commits the delivery, then calls C05. For a wall-clock closure and detour, use the full walkthrough with --fresh.

    docker compose up -d --build
docker compose exec -T api python -m app.components.c09_logistics_knowledge.demo_corpus
docker compose exec -T api python -m app.demo.c05 < contracts/components/c04-delivery-management/examples/delivery-submitted.json

    In PowerShell, use the following form for the last command.

    The CLI prints the committed plan as JSON. Repeating it with the same inputs returns the same plan and decision IDs. The defaults for --run-id and --correlation-id come from the Dublin fixture. Pass the delivery's original values when replaying another trace. The end-to-end check starts at C04's submit handler and requires evidence of its call to C05.

    Confirm a generated proposal (hop 5)¶

    Sign in as an operator, submit a Dublin simulation delivery and select Review plan. The saved-example CLI also prints a /plans?… link. The Plans page loads the proposal for that run and displays Confirm plan above the vehicle assignments. The URL carries planId, scope, runId and the original correlationId. The shell sends the selected X-Acting-Provider and the delivery's X-Correlation-ID on the read and confirmation. The page shows the saved plan ID and version, including after a revision. Vehicle allocation follows asynchronously.

    For a delivery submitted through C04, reading and confirming its proposal requires an operator acting for the provider that owns the delivery. A different acting provider receives HTTP 404 on a read, confirmation or confirmation retry, including within the same shared run. Imported Dublin examples carry fixture provenance and are shared with operators authorised for that run. The local fixture confirmation CLI accepts only those imports.

    The action sends POST /api/v1/plans/{planId}/confirmation with the saved version in expectedVersion, the same runScope, and a stable Idempotency-Key. C05 calls C04's markRequestsPlanned on the same PostgreSQL connection. C04 checks each delivery version and records the link and its C10 audit under the C05 service identity. C05 records C05.confirmPlan with the operator principal and request correlation ID from C02. Both audits, the next confirmed version with its original decision ID, the receipt and the first PlanReady outbox entry commit together. A retry of the same successful command returns its receipt without another success audit or event. A conflicting version requires a fresh read. If C05 rejects an authenticated confirmation, it records the outcome in a separate transaction after any business rollback.

    The c05-publisher worker sends the committed envelope to the topic exchange with routing key PlanReady. It marks the row published after RabbitMQ confirms receipt. If that mark is lost, the worker sends the same event ID again. Concurrent publishers can process different plans or runs. For one plan in one run, the confirmation event must have a committed publication mark before a worker can claim the revision event. The integration test receives the message and checks it against the saved row and the C08 event contract. Run it from backend/ with TEST_DATABASE_URL pointing to a dedicated test database and TEST_RABBITMQ_URL pointing to the test broker.

    uv run pytest tests/test_c05_confirm_plan.py tests/test_c05_outbox_publisher.py

    Read a confirmed delivery route for allocation¶

    C08 can use two in-process functions from app.components.c05_planning.allocation. Both take a SQLAlchemy connection and the RunScopeSelector built from the received PlanReady envelope's scope and runId.

    Operation Result
    get_delivery_route(conn, run_scope, plan_id, plan_version, delivery_id) Ok(ConfirmedDeliveryRoute) contains the saved plan, its single matching route and the same version's offset-aware planned_departure_at. Pass the plan ID and version from the event payload and the delivery ID from its requirement.
    check_current_version(conn, run_scope, plan_id, plan_version) Ok(None) when that version is the current confirmed plan. A different head or an unconfirmed head gives Conflict. An unknown plan in that scope gives NotFound.

    The first read also works for an older confirmed version. A proposal, unknown version, different run or delivery with no matching route gives NotFound. Multiple matching routes give Invalid. The returned plan includes the decision ID and resource requirements for checking the envelope.

    For an allocation, call the current-version check immediately before saving the commitment, on the same connection inside with engine.begin() as conn:. Use PostgreSQL READ COMMITTED. On success, C05 holds a shared plan lock until that transaction ends. Confirmation and future revision writers must take the matching exclusive lock with store.lock_plan before advancing the version. A failed check must prevent the allocation from being committed. With DBAPI autocommit, a different isolation level or no active transaction, the check returns Unavailable. Let database exceptions leave the transaction so the worker can retry after rollback with the event still unprocessed.

    With a dedicated PostgreSQL database and RabbitMQ broker configured as above, run the following from backend/. The broker test reads the Dublin route using the identifiers from the delivered message. The lookup tests add a later confirmed version to check historical reads and concurrent allocation checks.

    uv run pytest tests/test_c05_confirm_plan.py tests/test_c05_allocation_lookup.py

    findAffectedWork(changeScope) → Result\<AffectedWork>¶

    C07 asks C05 which unfinished work a change touches. C05 owns plans, so it decides what "affected" means for a route; C07 only says where and what changed. For the slice, C07 sends one call per changed segment.

    Examples request and response.

    Request: changeScope

    Field Type Required Meaning
    segmentKeys array of string one of Segments whose condition changed
    resourceIds array of UUID one of Resources whose availability changed or failed
    planIds array of UUID one of Plans named directly (for example by OperationalDisruption)
    from / to timestamp no Include routes overlapping [from, to). Omitting from uses the C05 clock at discovery. Omitting to leaves the window open-ended.
    scope enum yes live or simulation, copied from the event that triggered the detection
    runId UUID when simulation Simulation run; must be absent when scope is live

    Response: AffectedWork

    Field Type Required Meaning
    items array yes Empty when nothing is affected
    items[].planId UUID yes Plan touching the scope
    items[].planVersion integer yes Current version C05 checked against
    items[].deliveryIds array of UUID yes Unfinished deliveries on the affected part; completed ones excluded
    items[].matchedSegmentKeys array of string no Which of the requested segments the route uses
    items[].matchedResourceIds array of UUID no Which requested resources the plan relies on

    Failures: Invalid, Unavailable (C07 then reports disruption status unknown).

    requestReplan(context, planId, trigger, key) → Result\<ReplanOutcome>¶

    C07 sends one requestReplan per affected plan. The call is synchronous: C05 answers with a final outcome straight away.

    Examples request, saved outcome and conflict failure.

    Request

    Field Type Required Meaning
    context AuthContext yes Service identity C07, plus correlationId
    planId UUID yes Plan to revise
    trigger.disruptionId UUID yes Disruption record behind the request
    trigger.disruptionVersion integer yes Version of that record
    trigger.basedOnPlanVersion integer yes Plan version returned by findAffectedWork
    trigger.reason enum yes road_closed / congestion / resource_unavailable / operational_failure / weather
    trigger.citySnapshotVersion integer no Snapshot the disruption was judged on
    trigger.sourceEventId UUID yes Event that started the chain
    scope enum yes live or simulation, copied from the event that triggered the detection
    runId UUID when simulation Simulation run; must be absent when scope is live
    key string yes Idempotency key = planId:basedOnPlanVersion:disruptionId:disruptionVersion

    Response: ReplanOutcome

    Field Type Required Meaning
    status enum yes NoChange / ReviewRequired / PlanSaved
    newPlanVersion integer when saved Version of the saved revision
    decisionId UUID when saved C10 decision record
    reason string when ReviewRequired Why no feasible revision was saved, for the operator

    Example review required. An infeasible revision is not a failure: it is Ok with status ReviewRequired and a reason.

    Failures: Invalid, NotFound, Conflict and Unavailable. C07 treats any Conflict as a stale plan; see Agreed with C07.

    The idempotency key is what stops the C08 → C07 → C05 loop. The same key always returns the first outcome again. Because the key includes basedOnPlanVersion, C05 also returns the saved result when that disruption version already produced a revision for that plan and run, even if a retry carries a newer basedOnPlanVersion.

    Run the Dublin replan¶

    The C07 worker uses its existing PlanningPort in-process. Discovery starts from the current confirmed plans in the event's partition and reads progress through C04. The revision locks the plan, checks its base version and rereads the linked deliveries. It queries C06 for the latest conditions on the current route and the detour. A selected detour uses the delivery's current van and capacity requirements, the C09 policy evidence and the saved delivery window. After evaluating the route, C05 asks C06 to hold that snapshot version through commit. If city conditions changed meanwhile, C05 returns Unavailable so C07 can retry against current facts. A stale plan version returns Conflict for C07's one rediscovery attempt. Once C05 holds that version, it rechecks departure, road validity and the delivery deadline at decision time. If the detour no longer fits, it records ReviewRequired and keeps the current plan. The fixed route covers one unfinished Dublin delivery. An explicit open report for Abbey Street Lower must cover the full eight-minute trip. A reported delay or a speed too low for the 1,600 m detour requires operator review. C08 owns the vehicle and driver commitment.

    The revision, C10 decision with its evidence, request receipt and revised PlanReady commit together. The event's causationId is the triggering CityStateUpdated.eventId. C07 receives PlanSaved after commit. Replaying the same saved disruption version can recover that result without advancing the plan or publishing a third event. NoChange and ReviewRequired record the reason and retain the current plan.

    The report follows the plan through the following records.

    Hop Evidence for this delivery
    3–4 C04's DeliverySubmitted outbox record and retained API logs identify the original submission and the actual in-process handoff for this delivery and plan. The C05 generation receipt and C10 decision identify the saved proposal and its C09 evidence. The checker reports PASS for the complete handoff and WIRED for generation from a saved example.

The current C04 generation and C07 replan ports take the run and trace.     Planning and persistence rules¶

    The C01 read and confirmation operations are in openapi.yaml. The API uses the shell's bearer token and provider context, enforces run access and returns error { code, message, correlationId } on these operations. Internal C07 calls use the typed Result contract. An initial proposal awaits operator confirmation. Confirmation checks its expected version, links its deliveries and queues PlanReady atomically with the confirmed state and decision references. A saved revision atomically records its expected-version update, C10-owned decision/evidence and PlanReady outbox entry.

    C10 evidence contains the exact passages and source/version/provenance used at decision time. Evidence is retained after the C09 corpus changes. An outbox publisher retries the saved event ID without rerunning planning. Failure to commit any authoritative state, evidence or outbox entry rolls back the operation.

    For UC07, trigger.citySnapshotVersion records the City State that triggered the request when C07 provides it. C05 reads current conditions in the same run and records the version it actually uses for the decision.

    The requirements list in the PlanReady payload describes all resource needs for unfinished deliveries in that plan version. C08 checks which existing commitments still satisfy those needs using the confirmed delivery route and departure.

    For the C05 → C08 handoff, the scoped lookup takes the event's planId, planVersion and run scope, plus the unfinished deliveryId. It returns the matching route and its plannedDepartureAt together from that confirmed version. The result identifies the scope, plan and version. plannedDepartureAt is an RFC 3339 timestamp with an explicit offset (Z or ±HH:MM). For example, the Dublin v4 lookup returns the route via seg:4471024, its 480-second duration and 2026-11-20T08:14:00Z. C08 uses this instant when checking the vehicle's local operating hours and rechecks the version before committing. A superseded version cannot advance the commitment. The Dublin fixture supplies the scenario start time for this demo lookup. C05 supplies the route's persisted departure in the integrated lookup.

    For mutating HTTP calls, a retry with the same caller, operation, run scope, key and request returns the first committed response. Reusing that key with a different request gives Conflict. Concurrent writes use expected-version checks. A lost response after commit is recovered by retrying the same request and key.

    Example sequence¶

    The proposal at version 2 is confirmed with expectedVersion 2, giving the confirmed plan at version 3. The earlier version 1 is outside this excerpt. After C06 records snapshot 42, C07 requests a replan based on version 3. The saved outcome refers to revision 4, which avoids seg:4471023. Versions 3 and 4 have the same van capacity requirement. The PlanReady event carries that requirement with version 4 and its decision ID. It retains the closure correlation ID and simulation run ID and has its own event ID. These are contract examples. A fresh walking-skeleton delivery starts at v1, confirms at v2 and takes the detour at v3.

    Agreed with C07 (#59, 20 Nov 2026)¶

    1. Run scope. ChangeScope and ReplanRequest carry scope (live or simulation) and runId, copied from the event that triggers the detection. runId is required for simulation and must be absent for live, the same rule as EventEnvelope. A simulation resolves only its run's plans, inputs and receipts; an unspecified run is never treated as live.
    2. Idempotency key. planId:basedOnPlanVersion:disruptionId:disruptionVersion. The key does not include the run scope; C05 scopes its receipts by run.
    3. Conflict. C07 treats any Conflict from requestReplan as a stale plan and retries once; if C05 needs to report key reuse differently, it should use a distinct failure. The retry is: call findAffectedWork once more (all the disruption's segmentKeys, same scope and runId), then send one new requestReplan with the planVersion C05 now reports, which gives a new key. C07 does not retry if the plan is no longer affected, or if C05 reports the same planVersion as before (the key would be identical). A second failure leaves the replan not made. C05, for its part, returns the saved result when that disruption version already produced a revision for that plan and run.
    4. ReplanOutcome. It gains reason (text, optional), required when status is ReviewRequired. Infeasible is no longer a failure. The remaining failures are Invalid, NotFound, Conflict and Unavailable.
    5. PlanSaved. C05 returns the committed revision's newPlanVersion and decisionId after saving the revision and its PlanReady outbox entry together. C05 owns the publication state. C07 owns recording the returned version for the Disruptions view.
    6. Port. PlanningPort returns a typed Result (app.shared.result: Ok or Failure) from both calls, instead of raising exceptions.
    7. Unavailable and retry. C07 marks the detection result as retryable only when delivering the event again can change the outcome:
    8. If C05 answers Unavailable to findAffectedWork, C07 reports unknown and does not mark the event as processed, so the event is not lost.
    9. If a requestReplan is not made because C05 answered Unavailable (including the rediscovery after a Conflict), C07 keeps the disruption with that plan as not requested and the result is retryable. When the event arrives again, C07 sends only the plans still pending, with the same key, so C05 deduplicates on it. A pending plan whose version has moved on still follows the Conflict rule of point 3.
    10. Causes a redelivery would not change do not set retryable: NotFound, a plan that is no longer affected, a repeated Conflict or one with the same planVersion, and Invalid. Those plans stay not requested, so the event is not retried forever.
